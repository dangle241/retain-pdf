# inputImage description

## Structure and alignment relationships
- `json_full.json` Top-level contains `layoutParsingResults`、`preprocessedImages` 和 `dataInfo` Three main blocks. In this example `layoutParsingResults` Paginated array. Each item contains: `prunedResult`、`markdown`、`outputImages` and `inputImage` and other fields,`inputImage` 里的 URL such as `…/input_img_{页号}.jpg`and `preprocessedImages` 里 `preprocessed_img_{页号}.jpg` Keep strict one-to-one correspondence (both arrays have same length).  
- `dataInfo.pages` is a per-page list. `width` and `height` used to ensure backend parsed coordinates map back to `inputImage`/`preprocessedImages` canvas sizes. That is: `layoutParsingResults[i]`, `preprocessedImages[i]`, `dataInfo.pages[i]` represent same source page; `inputImage` is input to layout parser.

## inputImage Role throughout chain.
- **Provider adapter**: in `document_schema` adapter: `layoutParsingResults` main structure. `inputImage` helps adapter parse layout maps 1:1 to original image (for verification of pageIndex, dimensions, or display ratio). If page-level trace needed (e.g. `layoutParserResult` box `page_id`), this field confirms current data's source image aligns with `dataInfo.pages` width/height, generating normalized document consistent with visual preview.
- **Trace / Log chain**: during troubleshooting, bind `inputImage` and `preprocessedImages` URLs to `trace_point` or `reporting` for later observation of layout results (especially adversarial OCR misjudgment or provider upgrade reproducibility). If layout parser provides error without context, use source text, renderer, or debug explorer to input cropped or scaled image for confirmation.
- **Frontend preview**Frontend needs to display layout overlayUse stdlib. layout parser Same image `inputImage`(input processed provider Standard preprocessing before analysis.`preprocessedImages` Better for display provider the output 'normalized view', but `inputImage` Only then layout parser Frontend uses actual loaded graph. canvas Background prevents canvas size and detection result mismatch.
- **Rerun / Cache**: `inputImage` carries authorization signature and timestamp, may expire. Cache strategy should at least cache URL (or local copy) so later reruns don't depend on provider online resources. On rerun, provider adapter checks `inputImage` consistency to verify old vs new layout output inconsistency. Cache can hold `inputImage` with `layoutParsingResults` to facilitate regenerating `normalized_document` or `reporting` without re-invoking OCR.

## Retention policy recommendations
1. `layoutParsingResults.inputImage` and `preprocessedImages` array order must stay synchronized; any provider adapter or regression tool must validate `page_count`/`numPages` when used.
2. `inputImage` link valid short-term. When archiving, choose: download or URL + version info in storage (e.g. `reporting` metadata) to ensure trace/renderer can later request again.
3. `preprocessedImages` for display provider processed result, but layout reproduction/debugging should use `inputImage` first because it is actual layout parser input. If both retained, frontend can alternately display "original viewport (`inputImage`)" and "standardized view (`preprocessedImages`)".
4. rerun/caching If layers reuse old paths, confirm corresponding. `dataInfo.pages` Size and `layoutParsingResults` Page numbers consistent, avoid because `inputImage` Expired `preprocessedImages`/`layoutParserResult` Cannot complete playback.

From above, treat `layoutParsingResults.inputImage` as layout parser canonical input, `preprocessedImages` as provider normalized preview; both with `dataInfo.pages` form page-aligned triangle relationship, providing consistent visual baseline for adapter, trace, frontend, and rerun/cache.
