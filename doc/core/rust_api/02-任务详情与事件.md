# Task details and events

How to read the task execution process.

## Main interface

Task Details:

- `GET /api/v1/jobs/{job_id}`

Event stream:

- `GET /api/v1/jobs/{job_id}/events`
- `GET /api/v1/ocr/jobs/{job_id}/events`

Failure diagnosis and recovery:

- `GET /api/v1/jobs/{job_id}/diagnostics`
- `GET /api/v1/jobs/{job_id}/resume-plan`
- `POST /api/v1/jobs/{job_id}/resume`

- `ocr_job`

- `glossary_summary`
- `log_tail`

Recommended frontend usage:

- Current main status view-only. `stage_snapshot`
- Check stage panel status. `stages`
- Event stream handles history, timeline, and troubleshooting only.
- View current stage description `stage_detail`
- `stage` Internal backend machine stage. Not a basis for frontend major stage judgment.
- View current task's actual stage. `runtime.current_stage`
- Total Time `runtime.total_elapsed_ms`
- Current phase duration `runtime.active_stage_elapsed_ms`
- View process timeline `runtime.stage_history`

## Timeline source of truth

runtime.stage_history is the true source of the main timeline; do not infer from /events.

Each item typically includes:

- `stage`
- `detail`
- `enter_at`
- `exit_at`
- `duration_ms`
- `terminal_status`

## Event stream

Event stream suits status cards, progress display, and troubleshooting, not the main timeline. Main timeline still view. `runtime.stage_history`。

GET /api/v1/jobs/{job_id}/events returns events after Rust canonicalization, not the original Python events. In public events:

- `display_stage` This is a stage snapshot./User stage in event can only be `ocr | translation | render | null`, will never be `done`。
- `stage` Backend internal machine stage, e.g. `ocr_processing`、`translating`、`rendering`。
- `substage` is a machine-readable substage, e.g. `translation_batches`、`render_prewarm`。
- lane distinguishes main progress from background/artifact/diagnostic events.
- `event_type` Normalizes event types, e.g. `progress`、`artifact`、`terminal`、`error`、`diagnostic`。
- `message` / `stage_detail` Human-readable only. Frontend must not rely on them for stage detection.
- The original Python stage / user_stage / event_type will be saved in payload.raw_stage, payload.raw_user_stage, and payload.raw_event_type for later troubleshooting.

`progress` Public progress object:

```json

  "unit": "page",
  "current": 37,

  "percent": 26.056338028169012

```

Frontend status cards prioritized.

- `display_stage`
- `lane`
- `substage`
- `stage_detail`
- `event_type`
- `progress.unit`
- `progress.current`
- `progress.total`
- `progress.percent`

Do not prioritize consuming these internal/Compatibility fields:

- `payload.raw_stage`
- `payload.raw_user_stage`
- `payload.raw_event_type`
- `message`
- `provider_stage`

`lane` Used to distinguish main progress from background events:

- main: can be displayed on the main status card.
- `background`Background warm-up, preparation, etc., should not override the main phase.
- artifact: artifact publication.
- `diagnostic`Diagnostic or error assistance information.

Progress rules:

Progress rules:
- Steps like `render_compile` must not display progress as "Total N Page"
- `render_prewarm` Backend lane, should not override `render_pages` of the main progress.
- Completion events should include final data whenever possible. `current=total`Restore state after refresh.

## Failed protocol

On failure, check first:

- `failure.summary`
- `failure.category`
- `failure.root_cause`
- `failure.retryable`
- `failure.suggestion`

Compatibility fields:

- `failure_diagnostic`
- `log_tail`

Frontend: if only clean failure info for task detail page, prefer reading:

`GET /api/v1/jobs/{job_id}/diagnostics`

Return fields:

- `failed_stage`
- `failed_substage`
- `summary`
- `detail`
- `suggestion`
- `retryable`
- `resume_available`

This interface will reuse failure as the official field; fall back to the backend classifier if needed. No frontend parsing of request_payload, events, or log_tail.

## Breakpoint recovery

Recovery plan:

`GET /api/v1/jobs/{job_id}/resume-plan`

Return fields:

- `can_resume`
- `job_id`
- `from_stage`
- `resume_workflow`
- `reuses_artifacts`
- `reruns_stages`
- `reason`

Current rules:

- If translations_dir + source_pdf exists: from_stage=render, resume_workflow=render — only re‑render.
- If normalized_document_json + source_pdf exists: from_stage=translate, resume_workflow=book — rerun translation and rendering.
- Two types checkpoint None.`can_resume=false`，`reason` Provide the reason.

Execute recovery:

`POST /api/v1/jobs/{job_id}/resume`

Reuse current implementation `/rerun` Execution Contract:

- Preserve original when re-rendering in place. `job_id`Clear old render artifacts; queue. `render` workflow。
- If only an OCR checkpoint exists, create a new book resume job.
- If task still ongoing. `queued` / `running`Status conflict. Cancel first.

## Key Takeaways

- Detail page main API: `GET /api/v1/jobs/{job_id}`
- View Timeline `runtime.stage_history`
- View event stream `GET /api/v1/jobs/{job_id}/events`
- View the true source of failure. `failure`
- View concise failure info `GET /api/v1/jobs/{job_id}/diagnostics`
- View restore button state. `GET /api/v1/jobs/{job_id}/resume-plan`
