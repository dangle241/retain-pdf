# Task lifecycle

## 1. Currently supported workflow

The Rust API now supports 4 types of workflows:

1. `book`
   Current complete main flow identifier:OCR -> Normalize -> Translate -> Render
2. `ocr`
Only run OCR/Normalize, producing document.v1.json
3. `translate`
   OCR -> Normalize -> Translate, stops at translation artifacts, does not enter rendering
4. `render`
   Reuse existing job artifactsRe-render only.

## 2. Main chain

### 2.1 `book`

Here book is the workflow label in the current API contract: the complete main chain.
Stable enum. No frontend or local entry required to continue. provider Name exposed to user.

1. Upload PDF
2. Create main task
3. Internally create an OCR subtask
4. OCR provider Upload poll download result
5. Normalize to `document.v1`
6. Translate
7. Render
8. Output PDF / ZIP / other artifacts

### 2.2 `translate`

1. Upload PDF
2. Create translation task
3. Internally create an OCR subtask for the translation task
4. OCR provider upload, polling, and download results
5. Normalize to document.v1
6. Translate
7. Output translation payload, translation-manifest.json, and diagnostic information

Supplement:

- `translation.math_mode=placeholder` Use old formula protection chain during translation.
- `translation.math_mode=direct_typst` Translation stage: use experimental "formula direct-output" branch.
- Two unchanged task interface render entry. Only affect formula handling strategy translation phase.

### 2.3 `render`

1. Create Render Task
2. Pass in request `source.artifact_job_id` Point to an existing one job
3. Backend reuses source_pdf and translations_dir from this job
4. Render only
5. output new PDF / Typst / Rendered output

## 3. OCR subtask

book and translate tasks are split into OCR subtasks, typically:

`{job_id}-ocr`

There are two benefits to doing this:

- OCR transport Observable separately from the main translation rendering pipeline.
- OCR provider diagnostics can be returned separately in the details.

## 4. Common stage names

Stage names change as the pipeline progresses; common ones include:

- `queued`
- `ocr_submitting`
- `ocr_upload`
- `mineru_upload`
- `mineru_processing`
- `translation_prepare`
- `normalizing`
- `translating`
- `domain_inference`
- `page_policies`
- `rendering`
- `finished`
- `failed`

Supplementary note:

- `translate` Stops at general case. `translating -> finished`
- `render` Enter directly. `rendering`
- ocr will not enter translating or rendering

Not every task follows identical stages. Main logic remains consistent.

## 5. How to distinguish on the request side

Two things matter most:

1. `workflow`
Determines whether this is a full task, OCR‑only, Translate‑only, or Render‑only
2. `source`
   - `upload_id`Used for `book` / `translate`
- artifact_job_id: used for render

Current conventions:

- `workflow=translate` Still created. OCR Subtask, not rendered.
- `workflow=render` Won't run anymore. OCR or translate, but reuse existing. job artifacts
- workflow=ocr uses the standalone /api/v1/ocr/jobs entry; do not submit via /api/v1/jobs
- The JSON request body for /api/v1/jobs uses the formal grouped structure source / ocr / translation / render / runtime.
- Legacy flattened fields kept only in a few locations. multipart Auxiliary entry: not primary. JSON Contract Promotion

## 6. Frontend: understand phases

Suggest distinguishing three layers:

- `status`: Whether the task is finished
- `stage`Current stage?
- `stage_detail`Current Phase: Human Instructions

For example:

- `status = running`
- `stage = translating`
- stage_detail = Completed batch 18/55 of translation

This indicates:

- The task is not finished yet
- The current stage is translation
- Current batch progress has reached 18/55

## 7. Download button enabled when file ready.

Frontend should not construct rules itself; instead, directly read from the detail API:

- `actions.*.enabled`
- `artifacts.*.ready`

For example:

- PDF Download button view `actions.download_pdf.enabled`
- The ZIP download button depends on actions.download_bundle.enabled

Supplementary note:

- `translate` Incomplete source. Provide full string. bundle ready，PDF Not required. ready
- `render` After task success,PDF Should readybut not necessarily OCR Related Downloads

## 8. Check logs. Identify error. Fix root cause.

Failed tasks: check first:

- `failure.category`
- `failure.summary`
- `failure.root_cause`
- `failure.retryable`
- `failure.suggestion`

If still insufficient, review again:

- `runtime.final_failure_category`
- `runtime.final_failure_summary`
- `log_tail`
- `/events`

## 9. Timeline: chronological display. Event stream: real-time data ingestion.

This division of labor is critical:

- `runtime.stage_history` answers "how long each stage of the entire process took"
- `/events` answers "what specific events occurred during the process"
- `failure` answers "how this failure is categorized, whether it is retryable, and suggested handling"
- `failure_diagnostic` Simplified view for legacy frontend compatibility.

Former for overview, latter for troubleshooting.
