# Collaborative Development Guidelines

This document is not an API specification; it defines boundary conventions for backend collaborative development.

One goal only:

- Concurrent development `rust_api` When modifying, keep changes separate; avoid overlapping responsibilities; don't disrupt structure.

## 1. Module responsibilities

Default: collaborate per these boundaries:

- `routes/*`
- Only do HTTP adapter work
  - Handles request parsing, post-authentication entry, and response wrapping.
  - Do not aggregate business logic. Do not concatenate directly. job command
- `services/jobs/*`
  - Responsible for business logic within the task domain.
  - Include query、presentation、creation、control
  - This is where most business changes land first.
- `services/job_snapshot_factory.rs`
- Responsible for job snapshot/command assembly
- `services/job_launcher.rs`
- Responsible for job persistence and startup execution
- `services/runtime_gateway.rs`
- Responsible for services accessing runtime capabilities
- `job_runner/*`
  - Responsible for runtime execution.
  - Includes queueing, cancellation, process launching,OCR Subtask handoffrender/translate Execution chain
- `models/*`
- Only contain DTOs, input/output models, and persistence models
  - No new business orchestration or file system read logic.

## 2. Dependency rules

Default dependency direction:

- `routes -> services -> job_snapshot_factory / job_launcher / runtime_gateway / db`
- `job_runner -> db / config / runtime state`
- models must not reverse‑depend on routes or services

Default prohibited:

- `routes` Write complex business logic directly.
- `models/view.rs` Reintroduce file reading, failure diagnosis aggregation, and similar logic.
- Assembly Only helper continues to directly consume `AppState`

## 3. AppState usage conventions

`AppState` Allowed locations:

- Route entry points
- Lifecycle entry points
- Runtime module that actually coordinates cancellation, execution slots, and process launch.

Prioritize narrow dependencies.

- Build Commands
- Snapshot assembly
- Upload validation and storage.
- Read‑only view aggregation
- Persist to DB only./drop event helper

If a function only needs the resources below, don't pass them. `AppState`：

- `&Db`
- `&AppConfig`
- `&Path`
- `&RwLock<HashSet<String>>`
- `&Arc<Semaphore>`

## 4. New requirement landing rules

In multi-person collaboration: classify requirement first, then code.

- Add search fields, detail display, and artifact view.
- Prioritize changes in services/jobs/presentation or services/jobs/query
- Adding creation parameters and submission workflow/bundle logic
- Prioritize changes in services/jobs/creation
- Add execution phase, subtask handoff, cancellation semantics.
  - Prioritize changes `job_runner/*`
- Add public response fields or input fields.
- Modify models/*
- Only HTTP input/output parameter changes
- Modify routes/*, but try not to leave business logic in the route

## 5. Common anti‑patterns

Collaboration pitfalls that rot code structure:  Code reviews skip deep reads. PRs too large to review. No shared style guide. Merge before tests pass. Feature branches live forever. No rollback plan. Docs lag behind code. Tests mock everything. No shared understanding of "done". Tech debt piled on "quick fixes".

- In route, read the DB, piece together views and commands, and check the file system [command] df -h [to see disk usage].
- In services, directly write HTTP semantics
  - e.g., directly handle Header、Multipart、Response
- In job_runner, add new submodules that pass AppState through helpers
- In models, add aggregation logic that incidentally reads disk files.
- Refactor into separate functions. Single Responsibility Principle. ponytail: ceiling: 100-line functions; upgrade path: extract to modules when >50 lines.  Split now.

## 6. Pre-commit minimum checks

If changes were made to `rust_api`By default, at least do the relevant items from the following:

- `cargo check --quiet`
- If creation / job_snapshot_factory / job_launcher is changed, add service mapping tests
- If the process runner/lifecycle is changed, add corresponding runner tests
- If query/presentation is changed, add corresponding query or presentation tests

If a change causes the lower layer helper starts depending directly on `AppState`Default: explain in review why this must be done.
