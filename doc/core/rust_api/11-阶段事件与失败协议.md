# Stage Events and Failure Protocols

This document defines the boundaries for Rust API and Python worker stage events, progress events, and failure objects.

Goal: the frontend no longer depends on message, log_tail, or stdout text to guess status.

## 1. Three-layer event sourcing

Current backend has three event layers.

1. Python raw pipeline events
- File: DATA_ROOT/jobs/{job_id}/logs/pipeline_events.jsonl
   - Writer:Python OCR / translation / render worker
   - Purpose: fine-grained progress within phase,artifact Publish & Failure Context

2. Rust DB events
   - Table:SQLite `events`
- Writer: Rust job runner
- Purpose: job creation, status changes, final state, and legacy event compatibility.

3. Rust API canonical events
- Interface: GET /api/v1/jobs/{job_id}/events
   - Assembler:`services/jobs/presentation/live_stage`
   - Purpose: the sole public event stream for frontend and third-party consumption.

Frontend consumes only the third layer. The first and second layers are backend-internal sources.

## 2. Python Original event contract

When Python writes to pipeline_events.jsonl, it must consistently include these fields:

```json
{
  "job_id": "job-123",
  "seq": 12,
  "ts": "2026-05-28T10:12:33Z",
  "created_at": "2026-05-28T10:12:33Z",
  "level": "info",
  "user_stage": "translation",
  "stage": "translating",
  "substage": "translation_batches",
"stage_detail": "Completed translation batch 18/55",
  "event_type": "stage_progress",
  "semantic_event_type": "progress",
"message": "Completed translation batch 18/55",
  "progress_current": 18,
  "progress_total": 55,
  "progress_unit": "batch",
  "provider": "",
  "provider_stage": "",
  "elapsed_ms": 193822,
  "payload": {}
}
```

Field rules:

- `user_stage`
  Python Side roughing stage, only allow:`ocr | translation | render | done`。
- `stage`
  Python Internal machine stage, e.g. `translating`、`render_preprocess`。
- `substage`
  Machine-readable substage: core field for frontend state semantics.
- `stage_detail`
  Source text missing. Provide the Chinese source to translate.
- `message`
  Log text: human-readable only; no machine semantics.
- `progress_current` / `progress_total` / `progress_unit`
Must align with the current user_stage + substage.
- `semantic_event_type`
Python normalizes semantics of old events like stage_progress / artifact_published; Rust will still re‑canonicalize.
- `payload`
  Only extension data, not primary semantics.

Prohibit such events:

```json
{
  "user_stage": "translation",
  "stage": "translating",
  "message": "render payload prewarm: ready"
}
```

Correct way:

```json
{
  "user_stage": "render",
  "stage": "render_preprocess",
  "substage": "render_prewarm",
  "message": "render payload prewarm: ready"
}
```

## 4. Rust canonical event contract

Rust API Event returned externally is not raw. Python line, but rather canonical event。

External field example:

```json
{
  "job_id": "job-123",
  "seq": 24,
  "ts": "2026-05-28T10:12:33Z",
  "created_at": "2026-05-28T10:12:33Z",
  "level": "info",
  "lane": "main",
  "stage": "translation",
  "substage": "translation_batches",
"stage_detail": "Completed translation batch 18/55",
  "event": "stage_progress",
  "event_type": "progress",
  "raw_event_type": "stage_progress",
  "progress": {
    "unit": "batch",
    "current": 18,
    "total": 55,
    "percent": 32.72727272727273
  },
"message": "Completed translation batch 18/55",
  "payload": {
    "raw_stage": "translating",
    "raw_user_stage": "translation",
    "raw_event_type": "stage_progress"
  }
}
```

Public `stage` represents the frontend display layer only:

- `ocr`
- `translation`
- `render`
- `done`

Public event_type provides the semantic category for translation.

- `progress`
- `artifact`
- `terminal`
- `error`
- `diagnostic`

`user_stage` Internal source field,API Output hidden by default. Frontend must not rely on it.

## 5. lane Rules

`lane` Used to resolve "background events overriding main state" issue.

- `main`
  Main progress. Status cards display.
- `background`
  Background warm-up, cache building, etc. Cannot override main stage.
- `artifact`
  Publish artifacts. Do not overwrite main stage.
- `diagnostic`
  Diagnostic and error assistance information.

Current fixed rules:

- `substage=render_prewarm` -> `lane=background`
- `event_type=artifact` -> `lane=artifact`
- `event_type=diagnostic` or Failure Assist Event -> `lane=diagnostic`
- Other Progress Events -> `lane=main`

## 6. Stage snapshot

GET /api/v1/jobs/{job_id} and the list API return the authoritative stage_snapshot, background_snapshots, and stages.

Select rules:

- Only from `lane=main` Primary selection phase.
- artifact and background events cannot override the main phase.
- `render_prewarm` This type of rendering preprocessing during translation enters `background_snapshots`。
- render stage priority displays `render_pages` page-level progress; `render_compile` is a step progress, cannot be disguised as total N pages.
- On failure, if final event has no progress, retain last trusted progress.
- `status=succeeded|failed|canceled` time `stage_snapshot=null`, the terminal state is expressed solely by `status` expression.
- `display_stage=done` Never appears.

In the detail API `stage_snapshot.progress` Current snapshot:

```json
{
  "current": 120,
  "total": 533,
  "percent": 22.5140712945591,
  "unit": "page"
}
```

Read-only detail API on frontend page refresh. `stage_snapshot` Determine current phase; event stream only for history, debugging, and timeline, not for current phase selection.`stage_detail` for copy only,`stage` Only backend internal machine stage.

## 7. Monotonic progress.

Python writer maintains `(user_stage, substage, progress_unit)` Maintain monotonic progress.

Requirements:

- Under the same key, progress_current must not regress.
- Different substages can count independently, e.g. render_pages and render_compile are independent.
- `render_prewarm` is background stepNot counted in main rendering page count.
- New or retry tasks must rewrite events; do not reuse old task events. seq。

## 8. Failure protocol

The formal failure object is the failure field in the job detail.

Example:

```json
{
  "failed_stage": "translation",
  "provider": "translation",
  "provider_stage": "continuation_review",
  "failure_code": "upstream_timeout",
  "failure_category": "timeout",
  "provider_code": null,
"summary": "Translation phase timeout",
  "root_cause": "provider timed out",
  "retryable": true,
  "upstream_host": "api.deepseek.com",
"suggestion": "Resume task from checkpoint",
  "last_log_line": "request timed out",
  "raw_excerpt": "timeout"
}
```

Field layering:

- `failed_stage`
  Prefer common failure phase. `ocr | translation | render | done`。
- `provider` / `provider_stage`
  Upstream or internal sub-stage ownership.
- `failure_code`
  Stable machine code.
- `failure_category`
  Coarse-grained error categories.
- `provider_code`
The upstream provider's original error code.
- `summary` / `root_cause` / `suggestion`
  Readable information for frontend and operators.
- `raw_excerpt`
  Anonymized original snippet.

`failure_diagnostic` Compatibility projection, not write target for new code.

When frontend needs clean failure messages, prefer:

`GET /api/v1/jobs/{job_id}/diagnostics`

This interface also exposes optional. `render_diagnostics`Data source is
`artifacts/pipeline_summary.json` Fields with the same name currently mainly record fallback behavior during the rendering phase.
For example, the fields typst_cover_fallback_pages and typst_cover_fallback_items locate where fallback occurred.
Physical delete fail fallback to logical delete. Typst The page of 'background coverage' and blockDoes not participate in failure classification, nor change.
`failed_stage` / `retryable` / `resume_available` semantics.

## 9. Acceptance criteria.

Event and failure protocol changes must satisfy:

- Frontend unreliable. `message` Judgment phase.
- render Related events not included. `user_stage=translation`。
- `render_prewarm` Do not overwrite main render progress.
- `/events` Output exposes public only. `stage` and stability `substage`。
- The progress snapshot in /jobs/{job_id} is available after refresh.
- Prefer failure information from failure, not log_tail or stdout text.
