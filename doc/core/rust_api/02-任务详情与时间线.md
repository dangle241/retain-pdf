# Task details and timeline

## 1. Main interface

The main interface for the task detail page is:

`GET /api/v1/jobs/{job_id}`

Most core info on the detail page should come from this one API:

- Current status
- Current stage
- Current phase description
- Runtime Timeline
- Failure Attribution
- Download button state
- OCR Subtask Summary
- Current task execution protocol summary
- Normalization Summary and Glossary Summary

## 2. Frontend-critical fields

Key fields in `data` Inside:

- `request_payload`
- `status`
- `stage`
- `stage_detail`
- `runtime`
- `failure`
- `actions`
- `artifacts`
- `timestamps`
- `log_tail`
- `normalization_summary`
- `glossary_summary`
- `invocation`

Among them:

- `request_payload` Snapshot of request parameters saved by backend for this task.
- Integration: to confirm a parameter reaches the backend, check here first.
- For example, the OCR page range should read: data.request_payload.ocr.page_ranges
- Formula translation mode should read:`data.request_payload.translation.math_mode`
- `invocation` Used to answer whether this task is the old path or the current one. stage spec Derived from path.
- `normalization_summary` Used to answer whether the normalization result is current. `schema_version=1.1`Default value narrowing occurred.
- `glossary_summary` Used to answer whether glossary enabled, hit/miss status.

## 3. Check `protocol` field in new task payload.

The current new version task should display:

```json
{
  "invocation": {
    "stage": "provider",
    "input_protocol": "stage_spec",
    "stage_spec_schema_version": "provider.stage.v1"
  }
}
```

Guidelines for integration testing:

- `input_protocol=stage_spec` Indicates this task uses current. spec-only worker
- stage_spec_schema_version specifies the specific stage spec version
- If unavailable here, not API failure; historical task may lack summary.

## 4. True source of the timeline

Overview -> process timeline" must use `runtime.stage_history` as the source.

Do not use /events to back‑infer the main timeline. The reason is straightforward:

- `runtime.stage_history` are already stage segments organized by the backend
- Each segment has entry and exit times.
- Each paragraph can directly attach final-state information.
- Frontend no longer needs merging, deduplication, inference.

## 5. `runtime` Need context. Which struct/table/API?

Current key fields:

- `current_stage`
- `stage_started_at`
- `last_stage_transition_at`
- `total_elapsed_ms`
- `active_stage_elapsed_ms`
- `retry_count`
- `last_retry_at`
- `terminal_reason`
- `final_failure_category`
- `final_failure_summary`
- `stage_history`

## 6. `stage_history` Fixed structure

Each item is a phase time segment:

```json
{
  "stage": "translating",
"detail": "Translating, batch 12/22",
  "enter_at": "2026-04-04T15:31:02Z",
  "exit_at": null,
  "duration_ms": null,
  "terminal_status": null
}
```

Field meanings:

- `stage`：Stage Name
- `detail`Stage entry instructions:
- `enter_at`Phase entry time
- `exit_at`Time to leave this phase; currently active phase is usually empty.
- `duration_ms`Stable only when phase completed; active phase usually empty.
- `terminal_status`Mark end phase. Check completion. `succeeded / failed / canceled`

## 7. How to read running tasks

If the task is still running:

- The currently active stage will also appear in `stage_history`
- This item typically `exit_at = null`
- This item typically has duration_ms = null
- Read current-stage real-time elapsed time. `runtime.active_stage_elapsed_ms`

In other words, the frontend should not use the current time on its own. - enter_atSource data use. Hard-calc display only for local frame interpolation. Interface source remain `active_stage_elapsed_ms`。

## 8. Read as: completed tasks

If task has ended:

- `status` Will be. `succeeded / failed / canceled`
- `runtime.terminal_reason` Explains the reason for the final state.
- `runtime.total_elapsed_ms` Total end-to-end time.
- `runtime.stage_history` Last item usually includes. `terminal_status`

## 9. `normalization_summary` Missing context. Provide source text or code snippet for translation/explanation.

In current task details `normalization_summary` is a lightweight summary, not a full report.

Key fields:

- `provider`
- `detected_provider`
- `schema`
- `schema_version`
- `document_defaults`
- `page_defaults`
- `block_defaults`
- `page_count`
- `block_count`

Recommended frontend usage:

- Page shows this summary read-only.
- If really need to investigate adapter/defaults/validation Details, then download `artifacts.normalization_report`

Note:

- Current main chain only accepts `schema_version=1.1`
- Here. `*_defaults` Represents default closing quantity; no longer called. `compat_*`

## 10. Historical tasks may lack a timeline.

Most easily misjudged area recently.

Legacy tasks may appear:

```json
{
  "runtime": null
}
```

This does not mean:

- Frontend misread.
- The current backend is down
- Task write failed.

It only means:

- At task creation and execution, backend had not persisted runtime timeline to DB.

Thus, frontend treats such tasks as "missing historical data".

## 11. “Missing field in historical tasks” and “Old task rejected” are distinct.

These are the two most easily confused concepts during recent joint debugging:

- `runtime = null`
  - Historical task data missing.
  - Task itself may still allow viewing details and event stream.
- Detail/download endpoint returns "Old task not supported".
  - Indicates task still in old directory layout or old. artifact Storage
  - The backend will no longer handle compatibility migration for it; rerun only.

## 12. Guaranteed range

The warranty scope in the current document is:

- Task created by the new backend
- Task executed entirely by same new backend.

Only within this range.`runtime.stage_history` Ensures full process, not just final stage.

## 13. Read order for frontend use

1. First read `status`
2. Then read runtime.current_stage
3. Direct timeline read. `runtime.stage_history`
4. Current stage: time-consuming read. `runtime.active_stage_elapsed_ms`
5. Total reading time `runtime.total_elapsed_ms`
6. For failed tasks, first check failure.summary and failure.category
7. Execute protocol read `invocation`
8. Normalized summary read `normalization_summary`
9. Read glossary summary `glossary_summary`

## 14. How to understand translation.math_mode

Translation pipeline currently supports two values:

- `placeholder`
- Default value
  - Continue to use the old formula protection / placeholder / Recovery Link
- `direct_typst`
  - Experimental mode
  - Do not do formula placeholder protection, directly let the model output the body text and `$...$` Math

Frontend: display or pass-through as string only; no inference.
