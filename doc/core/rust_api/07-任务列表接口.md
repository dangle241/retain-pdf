# Task list API

## 1. Main interface

Task list:

`GET /api/v1/jobs`

OCR Subtasks:

`GET /api/v1/ocr/jobs`

Both interfaces are suitable for:

- Recent Tasks
- Task History List
- Task panel after simple filtering.

## 2. Query parameters

Currently supported:

- `limit`
- `offset`
- `status`
- `workflow`
- `provider`

Note:

- `limit`
  - Optional; defaults to backend's built-in default.
- `offset`
- Optional, default 0
- `status`
- Optional
  - Current value:`queued` / `running` / `succeeded` / `failed` / `canceled`
- `workflow`
- Optional
- Current values: book / ocr
- `provider`
- Optional
  - Currently mainly used for pressing. OCR provider Diagnostic information filtering, e.g. `mineru`

## 3. Sort order

Current fixed rules:

- Ordered by updated_at DESC

That is to say:

- Recently changed tasks first
- Better for Recents panel
- Not equal "Recently created"

## 4. Return structure

Return wrapper:

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [
      {
        "job_id": "20260406063244-2176e4",
        "display_name": "paper.pdf",
        "workflow": "book",
        "status": "running",
        "trace_id": "trace-abc",
        "display_stage": "translation",
        "stage": "translating",
        "substage": "translation_batches",
        "lane": "main",
"stage_detail": "Translating, batch 3/12",
        "progress": {
          "unit": "batch",
          "current": 3,
          "total": 12,
          "percent": 25.0
        },
        "invocation": {
          "stage": "provider",
          "input_protocol": "stage_spec",
          "stage_spec_schema_version": "provider.stage.v1"
        },
        "created_at": "2026-04-06T06:32:44Z",
        "updated_at": "2026-04-06T06:33:00Z",
        "detail_path": "/api/v1/jobs/20260406063244-2176e4",
        "detail_url": "http://127.0.0.1:41000/api/v1/jobs/20260406063244-2176e4"
      }
    ],
    "invocation_summary": {
      "stage_spec_count": 1,
      "unknown_count": 0
    }
  }
}
```

Each item always includes:

- `job_id`
- `display_name`
- `workflow`
- `status`
- `trace_id`
- `stage`
- `created_at`
- `updated_at`
- `detail_path`
- `detail_url`
- `invocation`

The list response also includes an additional aggregation field:

- `data.invocation_summary`

## 5. Field. Context? DB column, struct member, or form input? Specify.

- `job_id`
  - Task unique identifier
- `display_name`
  - User-facing task name
  - Value precedence:
1. The uploaded source PDF filename
2. The final filename from the remote URL
    3. Final fallback. `job_id`
- `workflow`
  - Main task usually is: define scope. `book`
  - OCR Subtasks are typically `ocr`
- `status`
  - Current or final state
- `trace_id`
  - The current task is attached to artifacts on trace idMay be empty.
- `stage`
  - Current coarse-grained phase.
  - Suitable for list labels, not for replacing detail content. `stage_detail`
- `detail_url`
  - Main entry for subsequent requests after detail view opens.
- `invocation`
  - List-level execution protocol summary
  - Show new tasks `input_protocol=stage_spec`
  - Good for debug tags; not a replacement for the full check in details.
- `invocation_summary`
  - Protocol aggregation statistics in current pagination results.
  - Frontend lightweight prompt: "Has this page fully switched to the new protocol?"

## 6. Frontend recommended read method

Recent tasks list:

`GET /api/v1/jobs?limit=20&offset=0`

Failed tasks only:

`GET /api/v1/jobs?status=failed&limit=20&offset=0`

To view only OCR subtasks:

`GET /api/v1/ocr/jobs?limit=20&offset=0`

Recommended:

- Title:`display_name`
- Status:`status`
- Current stage: display_stage
- Current sub-phase:`substage`
- Current progress:`progress`
- Protocol:`invocation.input_protocol`
- Last updated:`updated_at`
- Click to enter:`detail_url`

## 7. Don't expect the list API to return anything.

Current list API does not directly return:

- `runtime`
- `runtime.stage_history`
- `failure.summary`
- `artifacts`

So if the frontend wants to display:

- Failure Summary
- Total time
- Download
- Process timeline

Click list item, then call detail endpoint. Do not overload list endpoint with all fields.

## 8. OCR List is subset of main list.

`GET /api/v1/ocr/jobs` Essentially just:

- Reuse same list logic.
- Additional Fix `workflow=ocr`

Therefore:

- Consistent return structure.
- Only data range differs.

## 9. Context missing. Provide code or design doc.

The purpose is straightforward:

- Keep list API lightweight.
- Detail API carries full state.
- Front page fast first; detail page fetches full data.

This is better than right off the bat... `runtime`、`failure`、`artifacts` Put everything into a list: more stable, easier long-term maintenance.
