# Rust API Response wrapper

## 1. Top-level Format

Rust API Currently, all responses use the same wrapper.

Successful response:

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

Failure response:

```json
{
  "code": 400,
  "message": "Detailed error message"
}
```

Reading rules is simple:

- code = 0 indicates success
- `message` is for humans to read
- Business data always persists. `data`

## 2. Common pitfalls

Many frontend blank pages, empty lists, fields "present in backend but not shown" — root cause not API missing data, but wrong read path.

Typical errors:

```json
{
  "items": [...]
}
```

This is not the current Rust API Structure.

Actual structure is:

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [...]
  }
}
```

That is to say:

- Cannot read file. `response.items`
- Cannot read. `response.data.items`, if your HTTP There is also an outer object at the client's outermost layer.
- Should ultimately read API In the response body. `data`

## 3. EventStream API examples.

`GET /api/v1/jobs/{job_id}/events?limit=50&offset=0`

Actual response structure:

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [
      {
        "job_id": "20260404150516-75857c",
        "seq": 1,
        "ts": "2026-04-04T15:05:16Z",
        "level": "info",
        "stage": "queued",
        "event": "job_created",
"message": "Task created",
        "payload": {
          "stage": "queued",
          "status": "queued",
          "workflow": "book"
        }
      }
    ],
    "limit": 50,
    "offset": 0
  }
}
```

The key here is:

- Event array at `data.items`
- limit is in data.limit
- offset is in data.offset

## 4. Recommended frontend unpacking order

For task details, lists, or event streams, it is recommended to process in this order:

1. First check the HTTP status code
2. Then check the response body for `code`
3. `code === 0` then read `data`
4. Never directly assume business fields are at the top level.

## 5. Judgment logic suitable for direct frontend implementation

- If HTTP is not 2xx, handle as a network or service error.
- If HTTP is 2xx but code !== 0, handle as a business error.
- If code === 0 and data == null, treat as success with no business payload.
- If the field should be `data.xxx`then don't look at the top level.
