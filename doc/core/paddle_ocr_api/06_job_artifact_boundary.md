# 06 Paddle Markdown to Job Artifact Mapping and boundaries

This document answers only one thing:

- Respective boundaries of the four layers: Paddle provider output, normalized_document, job artifact export/download interfaces?

Core conclusion first:

1. provider raw is the OCR provider's private output, for backtracking and diagnostics only—adapter input, not a downstream primary contract.
2. normalized_document is the OCR normalization phase's official deliverable. Main chain stable dependency.
3. job artifact is the job artifact registration and export layer. Exposes files as unified artifact keys, and does not redefine provider semantics.
4. The download endpoint HTTP exposed layer only promises 'download according to artifact' or 'download as stable resource' — it does not guarantee downstream understanding of the provider raw structure.

## One diagram shows boundaries

```text
Paddle API JSONL / result.json
  -> provider raw boundary
  -> document_schema adapter
  -> ocr/normalized/document.v1.json
  -> normalized_document boundary
  -> translation / rendering
  -> job artifacts registry / virtual bundle
  -> artifact export boundary
  -> /api/v1/jobs/* download routes
  -> download API boundary
```

Paddle provider Currently at provider-backed Original result file in the process:

- `ocr/result.json`

- `backend/scripts/services/ocr_provider/paddle_api.py`
download_jsonl_result() aggregates JSONL as:
  - `layoutParsingResults`
  - `dataInfo`
  - `_meta`

This layer's sole responsibility:

- Keep Paddle's original structure
- Provide input to the document_schema adapter
- For troubleshooting and provider Provide reconciliation evidence.

Responsibilities this layer should not bear:

- Should not be used directly as translation input
- Use as rendering input directly.
- Should not require Rust API or frontend understanding `layoutParsingResults` Field Details
- Should not wrap download interface as "unified document semantics".

That is to say:

- result.json is the provider raw snapshot
- It can change.
- Only adapter still stably maps it to `document.v1`Downstream should not be forced to change.

## 3. Paddle Markdown Which boundary?

In the current download layer, Markdown is not a formal contract field of the Paddle raw API, but a job-exportable artifact in the directory.

Rust Side parsing. Markdown Location:

- `backend/rust_api/src/storage_paths.rs`
  - `resolve_markdown_path()`
  - `resolve_markdown_images_dir()`

Current parsing order:

1. Priority read `job_root/md/full.md`
2. Prefer reading job_root/md/images/
3. Fall back only when compatible with the legacy layout: provider_raw_dir/full.md and provider_raw_dir/images/

This means:

- md/full.md and md/images/ belong to the job output structure
- They are "downloadable externally". Markdown Output
- They are not. Paddle raw provider contract itself

Thus, do not confuse:

- Paddle raw's markdown.text / markdown.images
- md/full.md / md/images/ in the job directory

The former belongs to. provider raw trace。
The latter belongs to job artifact/export Wording.

Current main chain already closed at this boundary:

- Paddle provider pipeline Executes once explicitly. markdown materialize
- Inject layoutParsingResults[*].markdown.text/images and publish to job_root/md/full.md and job_root/md/images/
- The Rust read-only layer only reads this set of published artifacts and no longer back‑infers from provider_raw_dir

There is a very important implementation constraint here:

- Markdown Relative image paths cannot be arbitrarily generated by us with a fixed pattern.
- Must use the keys from Paddle's markdown.images as the source of truth
- We currently only allow one layer of stable release packaging: publish the image to `md/images/` Add pagination. Add pagination to every page. `page-N/` Scope prefix to avoid multiple pages. PDF Images with the same name overwrite each other.

That is, if the original Paddle Markdown contains:

```html
<img src="imgs/img_in_image_box_320_138_932_438.jpg" ... />
```

Post-release Markdown should become:

```html
<img src="images/page-6/imgs/img_in_image_box_320_138_932_438.jpg" ... />
```

Among them:

- `imgs/img_in_image_box_320_138_932_438.jpg` This relative path comes from provider Raw Return
- `page-6/` Page scope we added for multi-page publishing.
- images/ corresponds to the job artifact directory md/images/

Cannot simplify error to:

- Fixed imgs/...
- Fixed assets/...
- Set a specific image naming template
- Pin specific Markdown Image syntax

Because Paddle The returned body may be either Markdown `![](...)`could also be HTML `<img src=\"...\">`, the relative path fragments must also fully follow provider Return value.

## 4. Job Artifact Export Boundary

job artifact Responsible for uniformly mapping files and virtual artifacts in the job directory to artifact key。

Key code:

- `backend/rust_api/src/storage_paths.rs`
- `backend/rust_api/src/services/artifacts.rs`

The key isn't "where to put the file" but "what to expose externally." artifact key”。

### Artifact keys directly related to Paddle/Normalize/Markdown

| artifact key | Meaning | Boundary ownership |
| --- | --- | --- |
| `provider_result_json` | provider Original Result Snapshot | provider raw |
| `provider_raw_dir` | provider Original directory | provider raw |
| layout_json | Historical/Compatibility layout results entry | provider raw or compatibility layer |
| `normalized_document_json` | Unify document contracts. | normalized_document |
| `normalization_report_json` | normalize Report | normalized_document Accessory |
| markdown_raw | Markdown file exported by the job | artifact export |
| markdown_images_dir | Markdown image directory exported by the job | artifact export |
| markdown_bundle_zip | Markdown bundle dynamically packaged by the API | artifact export |

### Boundary rules here.

services/artifacts.rs is only responsible for:

- Finding artifacts from the registry or fallback
- Generating stable resource paths for artifacts
- On-demand build. zip bundle

It is not responsible for:

- interpret Paddle raw JSON
- Defining document.v1 semantics
- Determine a specific block whether it is body text

That is to say, the artifact layer handles:

- whether the file exists
- which group the file belongs to group
- Which artifact key to expose
- Allow direct download?

artifact Layer should not be reversed. provider Semantic layer.

## 6. Coupling prevents independent deployment, scaling, and technology swaps. It creates cascading failures and makes testing impossible. Decouple to isolate change impact.

If the four layers are not separated, they will be repeatedly refactored later.

Typical erroneous coupling patterns:

1. Make the translation chain read Paddle raw layoutParsingResults directly
2. let artifact Export logic to understand `block_label/group_id`
3. Make download endpoint commit directly. provider Original field structure
4. Treat markdown.text as the downstream unified contract, instead of using document.v1 as the primary input

The correct way is:

1. provider raw Responsible for fidelity.
2. normalized document Responsible for unification
3. artifact export Responsible for registration and export.
4. download API Responsible for exposing according to stable resources.

Changes to each layer affect only that layer:

- Paddle API Changed: prioritize modifying provider adapter
- `document.v1` Enhanced: Edit normalize downstream consumers
- Download method changed: update artifact/export and route/facade

rather than changing the entire chain all at once.

## 7. Runtime evaluation rules

When encountering a field or file, first ask which layer it belongs to:

### Belongs to provider raw

Typical examples:

- `result.json`
- `layoutParsingResults`
- `dataInfo`
- `markdown.images`
- `group_id`

Rules:

- Can be kept
- Troubleshoot
- Cannot serve as primary chain official contract

Add one item regarding Markdown Image path determination rules:

- The keys in markdown.images are part of the provider raw semantics.
- published artifact Layer cannot rename its internal relative path structure.
- What is allowed is a “job markdown image directory wrapper + page scope isolation”, e.g. the images/page-6/ prefix
- Not allowed: removing the imgs/... internal structure returned by the provider and rewriting it with repository‑custom naming.

### Belongs to normalized_document

Typical examples:

- `document.v1.json`
- `document.v1.report.json`

Handling rules:

- This is the stable handover layer from OCR to translation/rendering
- Prioritize semantic enhancement adapter/schema Side Complete

### Belongs to artifact export

Typical examples:

- `markdown_raw`
- `markdown_images_dir`
- `markdown_bundle_zip`
- `provider_result_json`
- `normalized_document_json`

Handling rules:

- Focus on artifact key、ready Status, relative pathgroup、content type
- Do not invent provider semantics here.

### Belongs to download API

Typical examples:

- `/normalized-document`
- `/normalization-report`
- `/markdown`
- `/artifacts/{artifact_key}`

Handling rules:

- Focus on resource exposure, authentication, response headers.streaming

## 8. Documentation primary narrative

Use the following terminology for future discussions on this topic:

- `provider raw`：Paddle Original Output and Directory
- `normalized_document`Unify document contracts./Render formal input.
- `artifact export`Job artifact registration, packaging, and export.
- download API: external HTTP resource exposure

Don't mix these terms:

- “Markdown Exactly. Paddle Output
- "artifact is schema"
- Download endpoint equals provider contract”
- Only downloadable can serve as primary link input.

These statements recouple the layers.
