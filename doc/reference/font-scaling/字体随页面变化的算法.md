## Don't calculate font size yet. Define the problem first.

Put translated text back into original box; essentially one task:

**Fit text into limited rectangular space, preserving natural flow and original visual style.**

Actually, there are three concurrent goals:

1. Text must fit.  
2. Cannot appear overly abrupt.  
3. Should be consistent on the same page.  

If the sole aim is to make everything fit, the simplest approach is to shrink all text to a very small size. This will certainly prevent overflow, but the page will look unappealing.  

Chasing only "looks big" → overflow, overlap, bottom collision, crowding.  

So this isn't about "finding a fixed font size", but rather:

**Dynamically balance fit and fidelity.**

---

## II. First criterion for font size: Is this page loose or tight?

Let's first look at an intuitive example.

### Example 1Both are body pages, but page density differs completely.

Assume two paper pages:

- A Page: two-column body dense, tight leading, minimal whitespace.
- B Page: only a few short paragraphs, large image in middle, page very empty.

If forcing same font size on both pages:

- A Page may not fit; translation increases overflow risk.
- B Page too small and empty.

So the first check must be:

**Check page density first: dense or loose.**

This step needn't be complicated. Core: observe blocks resembling body text, note their usual rhythm.

- Average line height.
- How tight is line spacing?
- Approximately how many characters fit in the same width?
- Most body text blocks on the page: compact or spacious?

You can think of it as:

**Find base font size per page.**

Baseline not final. Anchor. Later blocks adjust around it.

## 3. Second basis: block box dimensions, especially width and height

Page baseline insufficient—blocks on same page differ entirely in context.

### Example 2: Two boxes on the same page

Assume two text blocks on same page:

- block AWidth 420, high 110
- Block B: width 180, height 110

They are the same height, but the width differs by more than double.

If both blocks use the same font size:

- A Low line-break pressure.
- B Line wrap pressure will be very high.

Especially after translation into Chinese, text in narrow boxes quickly wraps into many more lines once sentences grow slightly longer.  

So the second condition is:

**Same font size renders differently in wide vs narrow containers.**

Therefore the algorithm must focus on two geometric quantities:

- Box width: determines approximate characters per line.
- Box height: maximum lines tolerated.

Width primarily determines excessive line wrapping; height determines whether content fits after wrapping.

---

## 4. Third basis: translation expansion ratio vs source

The frame alone isn't sufficient; content must also be examined.

### Example 3: An English sentence that becomes significantly longer after translation

Original:

`The catalyst significantly improves conversion efficiency under mild conditions.`

After translation:

`This catalyst significantly improves conversion efficiency under relatively mild reaction conditions.`

Some language pairs have little length variation, but some blocks grow significantly, especially:

- Abbreviations expand when the source is English and the target is Chinese.
- Technical phrases expand after translation to Chinese
- When formula placeholders are present, reorganize surrounding text.

Now what matters isn't "what font size it was originally", but:

**Translation density exceeds box capacity by unknown margin. Measure rendered width/height against container bounds to quantify overflow.**

So a practical heuristic:

1. First estimate how many 'units of text' this box can hold at the current font size.
2. Re-estimate translated content approx required "unit text space" count.
3. Subtraction result shows current bias: loose or crowded.

"Unit text" need not be strict character count. Can be visual, e.g.:

- Estimate visual line count after wrapping.
- Characters excluding whitespace
- Apply different weights to formulas, punctuation, and long words.

The core idea is not a specific formula, but rather:

**Compare content requirements against box capacity.**

## V. Core: font size determined in three layers, not calculated once

A more stable dynamic algorithm usually isn't "one-shot brainstorming". It splits into three layers.

### Layer 1: Page sets baseline value.

First, based on the full page's body text density, assign a rough baseline for this page.

For example:

- Dense page: Baseline 9.2pt
- Normal page: baseline 9.8pt
- Relaxed page: Baseline 10.4pt

This step determines overall page tightness or looseness.

### Layer 2: each block self-corrects based on its frame and content.

Then look at this block:

- Is the frame particularly narrow?
- Is the height very limited?
- whether the translated text is significantly longer
- Are there many formulas and poor line-breaking space?

If answer skews "cramped", nudge down from page baseline.  
If the answer leans toward "loose," allow it to move up slightly.

This step determines whether this block is harder or easier to place relative to the average page state.

### Layer 3: final border check before render.

Even if the first two layers of judgment are reasonable, errors can still occur. Real rendering encounters many unforeseen things:

- Some glyphs wider than expected.
- Actual width differs from estimated width for mixed CJK-English text.
- Inline formula overflows the line.
- Punctuation distribution makes actual line breaks worse than estimated.

So a truly mature solution ultimately requires one final step:

**Measure with current font size. If still overflows, scale proportionally.**

This step is the final safeguard.

---

## VI. What the algorithm actually looks at: understand it as 5 Signal check

If we compress the above reasoning into the core criteria, it essentially comes down to these five signal types:

### 1. Page density.

Denser page, smaller base font size.  
The looser the overall page layout, the larger the base font size.

### 2. Frame width

Narrower box increases line-wrap pressure; font size must be more conservative.  
The wider the box, the more naturally the font size can hold its space.

### 3. Box height

The shorter the box, the fewer total lines it tolerates, and the riskier the font size becomes.  
Higher box, greater line-wrap allowance.

### 4. Text content density

The longer, denser, and harder to split the translated text, the smaller the font size should be.  
When content is short and semantic blocks are clear, font size is easier to maintain.

### 5. Special content ratio

for example, formulas, long tokenTheoretical capacity unreliable when many indivisible segments exist.  

So for such blocks, the algorithm is usually more conservative and does not enlarge font size as aggressively as for regular body text.

## 8. Why this algorithm outperforms linear scaling

Many systems initially use a very direct approach:

Font size reduce by same percentage as word count overage.

Useful but insufficient.

Because it assumes a premise:

**Text length scales linearly with layout pressure.**

But in reality, it is not.

For example:

- Same character count appears completely different in wide vs narrow box.
- With the same number of characters, presence or absence of formulas yields entirely different results.
- Same word count renders differently on a dense page versus a spacious one.

So a more reasonable algorithm is not just looking at 'how many extra characters', but making a comprehensive judgment:

- Was this page originally tight?
- Is this box difficult to place?
- Whether this content is difficult to lay out
- Still over after actual render?

In other words:

**Font size changes should use layered judgment and gradual convergence, not a single linear function.**

## 9. Common pitfalls of this approach

While better than fixed font sizes, this algorithm is also prone to pitfalls.

### 1. Overreliance on OCR

If OCR misidentifies two lines as one, it assumes large line spacing and loose content, overestimates page baseline. Later font sizing for the page may be too large.

### 2. Over-reliance on character count

Character count is a rough metric only. What truly determines typesetting pressure:

- whether line breaks are possible
- How many lines after line break?
- Any lines with overly wide content?

### 3. Lock minimum font size.

If a global hard lower bound is set, e.g., never below ... 9.6ptThen many extremely narrow frames will fail.  

Too low a lower bound noticeably degrades visual quality.

So the minimum font size should not be fixed, but should have some dynamism:  
Tolerance ranges can differ for normal text blocks, extremely dense blocks, and formula-dense blocks.

### 4. Estimate only. No final measurement.

No matter how smart the preceding steps, skipping a final real frame-fit check always leads to “estimated close, but actual overflow.”

---

## 10. Compress algorithm to one sentence

It can be summarized in one sentence:

**Check page average rhythm. Check box geometric pressure. Check content density. Finalize with real render.**

This is the core idea: font size scales with the page.

It is not for mathematical optimality, but for real-world PDF Get more stable, more natural, and less crash-prone results.

---

## 11. Final engineering summary.

A reliable dynamic font size algorithm typically doesn't ask:

Use 14px.

Instead, ask four consecutive questions:

1. What is the overall rhythm of this page?  
2. Relative to the entire page, is this block harder or easier to lay out?  
3. By how much does the translated content exceed the capacity of this box?  
4. After actual rendering, is it truly placed?  

Only after all four questions are answered will the font size seem more calculated than guessed.
