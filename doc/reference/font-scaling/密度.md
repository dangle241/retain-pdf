# How is density determined?

If you imagine a text box as a paper box, then "density" actually answers one sentence:

**Box fit: depends on content length vs box size. No data given. Need text + box dimensions.**

This question seems intuitive, but when it comes to code, you rarely consider just one metric. Because "crowded" has at least two meanings:

- Whether the content itself has grown longer
- whether this box itself has the capacity to accommodate this content

So in the current implementation, density is not a single constant; it is determined collectively by several groups of functions.

---

## Conclusion: two densities observed.

In the current implementation, the closest thing to "density" is not a function, but two lines:

1. **Length Density**
   - see whether the translated content is 'inflated' relative to the original
   - Corresponding function:`translation_density_ratio(...)`

2. **Layout density**
   - Content too cramped in box with current font size and line spacing?
- Function: `layout_density_ratio(...)`

In [fit.py](../../backend/scripts/services/rendering/layout/payload/fit.py) Both metrics evaluated together.

```python
length_density_ratio = translation_density_ratio(item, protected_text)
layout_density = layout_density_ratio(box, protected_text, font_size_pt=font_size_pt, line_step_pt=line_step)
is_dense_block = length_density_ratio >= COMPACT_TRIGGER_RATIO or layout_density >= LAYOUT_COMPACT_TRIGGER_RATIO
```

That is, the system does not only ask whether the translation has gotten longer, nor only whether the box is nearly full; it asks both.

## 2. Layer 1: Check for obvious content bloat

The most straightforward reasoning: if the original text has only a few words but the translation becomes a long passage, it is likely harder to layout.

This handled by [text_common.py](../../backend/scripts/services/rendering/layout/payload/text_common.py) `translation_density_ratio(...)` Handles error messages, short cases.

```python
def translation_density_ratio(item: dict, protected_text: str) -> float:
    source_words = source_word_count(item)
    if source_words <= 0:
        return 0.0
    zh_chars = translated_zh_char_count(protected_text)
    if zh_chars <= 0:
        return 0.0
    return zh_chars / source_words
```

This function does something very simple:

- Provide source text.`source_word_count(item)`
- then count how many Chinese characters are in the translation:`translated_zh_char_count(protected_text)`
- Use Chinese character count. / Source word count yields a ratio.

Its purpose is not precise typesetting calculation, but quick judgment:

**Yes. Chinese chars denser. English words longer. Same UI space → English wraps more.**

### Example

Assume a source block:

- Source word count:20
- Translated Chinese characters:18

So:

`translation_density_ratio = 18 / 20 = 0.9`

This indicates it has reached a tight edge.

If another block:

- Source word count: 20
- Translated Chinese chars: 24

So:

`translation_density_ratio = 24 / 20 = 1.2`

Such blocks are "obvious bloat"; treat more conservatively afterward.

Current threshold also written in same file:

- `COMPACT_TRIGGER_RATIO = 0.9`
- `HEAVY_COMPACT_RATIO = 1.0`

To put it bluntly:

- `>= 0.9`Instructions are getting tighter.
- `>= 1.0`: indicates it is already a heavily compact block

## Layer 2: At current font size, will this box actually overflow?

Content length check only. No frame inspection.

Also `ratio = 1.0` only means the content fits length-wise.

- Place in a wide 400pt In the body field, probably fine.
- In a 160pt wide Caption box, may overflow soon.

Thus the second layer must check the "capacity of the box".

this step is handled by `layout_density_ratio(...)` in [text_common.py](../../backend/scripts/services/rendering/layout/payload/text_common.py):

```python
def layout_density_ratio(
    inner: list[float],
    protected_text: str,
    *,
    font_size_pt: float,
    line_step_pt: float,
) -> float:
    width = max(8.0, inner[2] - inner[0])
    height = max(8.0, inner[3] - inner[1])
    zh_chars = translated_zh_char_count(protected_text)
    approx_char_width = max(font_size_pt * 0.92, 1.0)
    chars_per_line = max(4.0, width / approx_char_width)
    required_lines = max(1.0, zh_chars / chars_per_line)
    occupied_height = required_lines * line_step_pt
    return occupied_height / height
```

This function's logic can be translated into plain English:

1. Check frame width and height.
2. Assuming current font size, approximate width of one character.
3. Approximate characters per line?
4. Estimate how many lines the translated text will occupy.
5. Calculate final total height of these lines.
6. Divide occupied height by container height.

Result: intuitive ratio.

- `< 1.0`Theoretically, it still fits.
- `≈ 1.0`: already very tight
- `> 1.0`Theoretically already out of bounds.

### Example

Assume a box:

- Width: 180pt
- Height: 90pt
- Current font size:9pt
- Current line spacing:12pt
- Translated Chinese characters: 72

Rough estimate:

- Single character width approx. `9 × 0.92 = 8.28pt`
- Approx. per line `180 / 8.28 ≈ 21.7` character
- 72 characters. `72 / 21.7 â 3.3` lines
- Approx. height `3.3 × 12 = 39.6pt`
- Approx. layout density `39.6 / 90 = 0.44`

This shows that this block is actually not crowded.

If the same content is placed in another box:

- Width: 110pt
- Height: 48pt

Then:

- Each line can probably only hold `110 / 8.28 ≈ 13.3` characters
- 72 characters require `72 / 13.3 ≈ 5.4` lines
- Occupied height about `5.4 × 12 = 64.8pt`
- Layout density about `64.8 / 48 = 1.35`

This is a typical high-density block; the current font size is definitely too large.

## 4. Layer 3: How to calculate the box's "actual capacity"

The one above `layout_density_ratio(...)` Quick estimate, lightweight. Use for initial density screening.

The calculation that more truly approximates 'just how much content this box can hold' is in [capacity.py](../../backend/scripts/services/rendering/layout/payload/capacity.py)。

The core is `box_capacity_units(...)`：

```python
def box_capacity_units(
    inner: list[float],
    font_size_pt: float,
    leading_em: float,
    visual_lines: int | None = None,
) -> float:
    width = max(8.0, inner[2] - inner[0])
    height = max(8.0, inner[3] - inner[1])
    line_step = max(font_size_pt * 1.02, font_size_pt * (1.0 + leading_em))
    lines = max(1, int(height / line_step))
    if visual_lines and visual_lines > 1:
        lines = min(lines, max(1, visual_lines + 1))
    chars_per_line = max(4.0, width / max(font_size_pt * 0.92, 1.0))
    return lines * chars_per_line * 0.98
```

It does three things:

1. Calculate total lines based on font size and line spacing.
2. Calculate line capacity from box width.
3. Multiply width height get box total capacity.

There is a very critical detail here:

`visual_lines`

That is, it does not entirely trust 'how many lines the box height can hold', but instead refers to OCR / Layout structure estimates original block visual line count; avoid overoptimistic capacity.

## 5. Layer 4: Content requirements exceed simple character counting

If capacity is calculated, how is "demand" calculated?

This file contains `text_demand_units(...)` responsible for:

```python
def text_demand_units(protected_text: str, formula_map: list[dict]) -> float:
    formula_lookup = {entry["placeholder"]: entry["formula_text"] for entry in formula_map}
    return sum(token_units(token, formula_lookup) for token in tokenize_protected_text(protected_text))
```

It means:

- Split text into token
- Plain text counts as ordinary units.
- Formula placeholder not by 1 Characters not count. Cost align visual width.

Critical: character count understates formula pressure.

### Example

The following two text segments may have a similar character count:

1. `This method significantly improves material performance.`
2. `This method significantly improved.[[FORMULA_1]]Material performance under conditions.`

But the second section, with formulas, actually has heavier layout pressure.  

So the system will not treat them as the same requirement, but rather through `token_units(...)` Give formulas higher visual cost.

## VI. Layer 5: Why introduce it visual line count

There is an easily overlooked problem:

**Sometimes OCR Line count unreliable.**

For example, one that was originally replaced with 4 Line paragraph, by OCR Paste and Complete 1 Okay. At this point, if you only look at the original `lines`will severely overestimate the available space in this box.

So [measurement.py](../../backend/scripts/services/rendering/layout/typography/measurement.py) There is a dedicated set of functions to correct this.

- `plain_text_chars_per_line(...)`
- `_predicted_wrapped_line_count(...)`
- `visual_line_count(...)`
- `is_tall_single_line_glue(...)`

Where `visual_line_count(...)` idea is:

- First look at how many lines OCR says
- Estimate "expected line count for normal wrapping" based on text length, box width, and characters per line capacity.
- If the predicted row count is significantly higher than OCR Line count: use the more conservative count.

This step is not to calculate font size, but to prevent density judgment from being misled by false data.

### A typical example

Assume a case:

- OCR only gave 1 line
- But the box is tall, and the text length is... 140 characters
- Geometrically, one line cannot hold that much.

Now `visual_line_count(...)` will assume:

Not likely bug. 1 Main text, but rather OCR Multi-line paragraph pasted as one line.

The system then uses predicted values to correct subsequent capacity judgments. This yields density closer to the actual condition.

## 7. How density ultimately affects font size

The preceding functions do not directly return the final font size. Their purpose is to provide the typesetter with decision criteria.

Direct landing point at [fit.py](../../backend/scripts/services/rendering/layout/payload/fit.py) `fit_translated_block_metrics(...)`:

```python
capacity = box_capacity_units(box, font_size_pt, leading_em, visual_lines=visual_lines)
if capacity <= 0 or (demand <= capacity * 0.96 and layout_density < LAYOUT_DENSITY_SAFE_MAX):
    return font_size_pt, leading_em
```

The logic here is critical:

- If requirements do not approach capacity.
- Moreover, layout density is not excessive.

Keep current font size.

Conversely, if:

- `demand > capacity`
- or `layout_density` Already too high

Proceed to reduce font size and tighten line spacing.

That is, density does not directly output "9.2ptor8.8ptbut instead decide

- whether to shrink
- how many steps to shrink
- Only reduce font size, or compress line spacing too?

## 8. Treat as simple decision chain

If all functions were condensed into one plain sentence, roughly this chain:

1. **Check translation length. Flag if significantly longer.**
   - `translation_density_ratio(...)`

2. **Check height of this content in the box at current font size**
   - `layout_density_ratio(...)`

3. **Refine calculation: determine exact unit capacity of this box.**
   - `box_capacity_units(...)`

4. **Don't trust blindly OCR Line count, required `visual_line_count(...)` Fix applied.**

5. **End with "requirements vs Capacity determines font size reduction.**
   - `text_demand_units(...)` vs `box_capacity_units(...)`

## 9. Complete Example

Assume a translation block has these conditions:

- Frame width:145pt
- Frame height:62pt
- Default font size:9.4pt
- Line spacing:0.58em
- Original word count: 18
- Translated Chinese characters: 22
- With 2 formulas

System sees it as:

### Step 1: Check for content bloat

`translation_density_ratio = 22 / 18 ≈ 1.22`

This is already a heavy compact block.

### Step 2: Check if layout is too cramped at current font size.

Estimate by `layout_density_ratio(...)`:

- This box is narrow.
- 9.4pt Max line width 80 chars.
- Formulas increase actual line-break pressure.

The calculated layout density may approach or even exceed. `1.0`

### Step 3: Reassess capacity and requirements.

- `box_capacity_units(...)` The total capacity of the frame is somewhat small.
- `text_demand_units(...)` Formulas inflate requirements.

Thus, the conclusion:

**Dense block. Current font size unsafe.**

### Step 4: Enter shrinkage

`fit_translated_block_metrics(...)` Will start trying:

- Reduce font size incrementally first.
- If still insufficient, reduce further. leading
- Always test until requirement no longer obviously exceeds capacity.

This is the complete process of how density judgment actually affects font size.

## 10. Final summary

The so-called "frame density" is not essentially asking:

How many characters in this box?

But rather asking:

**Gap between box capacity and translation needs.**

In the current implementation, this issue is jointly answered by the following groups of functions:

- Page & Original Line Info Correction:
  - [measurement.py](../../backend/scripts/services/rendering/layout/typography/measurement.py)
- Text length & layout density estimate:
  - [text_common.py](../../backend/scripts/services/rendering/layout/payload/text_common.py)
- Capacity and Demand Calculation:
  - [capacity.py](../../backend/scripts/services/rendering/layout/payload/capacity.py)
- Shrink font size finally?
  - [fit.py](../../backend/scripts/services/rendering/layout/payload/fit.py)

If you keep tracing back, "why did the font size end up smaller," the answer usually circles back to this:

**Current block content nears or exceeds container capacity at this font size.**
